# 基于多模态 AI 的电力设备智能安全检测与风险评估系统

融合**可见光图像、红外热成像、电气时序**三类数据，输出 0–100 的风险分与四级风险等级
（正常 / 关注 / 异常 / 严重异常），并由大模型结合 RAG 知识库生成可解释的巡检报告。

当前以 **变压器** 为首个闭环设备，完成了从图像上传到报告落盘的端到端原型。

```
可见光图像 ─┐
红外热成像 ─┼─→ 多模态融合 ─→ 风险评估 ─→ 标准检索 ─→ AI 报告
电气时序   ─┘
```

---

## 一、背景与需求

### 1.1 背景

随着智能电网、数字变电站与无人机巡检的推广，电力设备巡检的数据形态已从单一可见光图像，
扩展为可见光图像、红外热成像、运行参数、电压电流波形与历史检修记录的混合体。

而现有巡检方式存在三个突出问题：

| 问题 | 具体表现 |
| --- | --- |
| **效率低** | 依赖人工逐张判读，难以应对无人机巡检产生的数据量 |
| **数据割裂** | 可见光、红外、电气量各自分析，缺少跨模态的关联印证 |
| **结论不可解释** | 单一算法只输出「异常 / 正常」，说不出依据哪条标准、该如何处置 |

近年目标检测、视觉语言模型（VLM）、时间序列深度学习与检索增强生成（RAG）的成熟，
为构建一个能同时解决上述三个问题的多模态系统提供了技术基础。

### 1.2 功能需求

1. 对可见光图像进行设备识别与外观缺陷检测；
2. 对红外热成像进行异常温升与热缺陷检测；
3. 对电压、电流、温度、功率等时序数据进行异常检测；
4. 对不同模态的检测结果进行融合分析；
5. 基于电力安全标准与设备技术文档进行知识检索；
6. 由视觉语言模型 / 大语言模型生成异常解释、风险说明与处置建议；
7. 自动生成结构化的电力设备安全检测报告；
8. 提供可视化平台展示检测结果与历史记录。

### 1.3 设计约束

三条贯穿全局、也是本系统区别于「直接调一个大模型」的关键约束：

- **大模型不承担底层检测。** 底层检测由视觉与时序模型完成，大模型只负责
  「解释、归因、建议」。安全判断不能被完全交给生成式模型。
- **阈值不由模型生成。** 所有权重、阈值、分级边界集中在
  [`config/config.yaml`](PowerAI-Safety/config/config.yaml)，作为系统的唯一事实来源，
  大模型只能引用和解释，不得改写。
- **缺权重不崩溃。** 模型权重缺失时对应分支自动降级为兜底实现，并在结果、报告与
  接口响应中**显式标注** `backend` 字段与警告信息，而非静默给出不可信结论。

## 二、技术逻辑

### 2.1 总体架构

采用「数据层 — 检测层 — 融合层 — 知识分析层 — 应用层」五层结构：

```text
┌──────────────────────────────────────────────────────────┐
│ 应用层     backend/main.py (FastAPI)                      │
│            /api/inspect  /api/inspections  /api/stats     │
├──────────────────────────────────────────────────────────┤
│ 知识分析层  backend/rag/    → 标准条款检索                 │
│            backend/llm/    → 解释、归因、处置建议          │
│            backend/risk/   → 规则判定 + 风险分级           │
├──────────────────────────────────────────────────────────┤
│ 融合层     backend/fusion/risk_fusion.py                  │
│            加权求和 + 权重重归一化 + 一致性加成            │
├───────────────┬──────────────────┬───────────────────────┤
│ 可见光分支     │ 红外分支          │ 电气时序分支           │
│ vision/       │ vision/          │ timeseries/           │
│ yolo_detector │ infrared_detector │ anomaly_detector      │
│ YOLO / 启发式  │ 辐射/灰度/伪彩     │ Transformer / 统计     │
├───────────────┴──────────────────┴───────────────────────┤
│ 数据层     data/samples/  data/uploads/  data/reports/    │
│            data/powerai.db (SQLite)   knowledge/          │
└──────────────────────────────────────────────────────────┘
```

编排入口是 [`InspectionService.inspect()`](PowerAI-Safety/backend/services/inspection_service.py)，
按「三分支 → 规则 → 融合 → RAG → 大模型 → 报告 → 落盘」顺序串联全流程。

### 2.2 三个检测分支

**可见光分支** — 目标是回答「哪里有问题」。以 YOLO 作为检测骨干，
区分**设备类**（transformer / bushing / terminal / conservator / radiator）与
**缺陷类**（oil_leak / rust / deformation / foreign_object / broken_part / oil_stain），
每类缺陷按严重程度配置贡献权重（如 broken_part 0.90、oil_stain 0.35）。
缺少训练权重时降级为基于显著性区域与边缘特征的启发式检测器。

**红外分支** — 目标是量化「有多热」。三条温度解析路径，按可得性依次降级：

1. `radiometric` —— 有 16 位辐射数据或 `.calib.json` 标定文件，得到真实物理温度；
2. `pseudocolor` —— 仅有伪彩色图，按配置的温度区间做线性映射；
3. `grayscale` —— 仅有无标定灰度图，只能得到相对温度分布。

核心判据是**相对温差** δ = ΔT / T₂（ΔT 为目标温度与参考温度之差），而非绝对温度——
因为环境温度与负载水平会整体抬升设备温度。同时计算三相温度不平衡度，
参考温度 T₂ 支持 `three_phase`（三相场景取中位相）与 `warm_median` 两种来源。

**电气时序分支** — 目标是发现「趋势上的异常」。流程为
去噪归一化 → 滑动窗口（96 点 ≈ 24 小时）→ 时域特征 + FFT + STFT → 模型判别。
模型路径为 Transformer 自编码器，以**重建误差**超过设定分位数判定异常；
无训练权重时降级为统计判据，涵盖 z-score 因子、负载率、电压偏差、三相电流不平衡等指标。

> 统计判据里有一处值得说明的设计：z-score 用的是「z 峰值 ÷ 纯噪声预期值」而不是 z 的绝对值。
> 因为 n 个标准正态样本的最大 |z| 期望约为 √(2·ln 2n)，n=96 时就有 3.2，
> 固定阈值 3.0 会把大量正常序列误判为异常。

### 2.3 多模态融合

第一版采用**结果级融合**，实现简单、稳定且易于解释：

```
RiskScore = w₁·VisualScore + w₂·ThermalScore + w₃·ElectricalScore + w₄·RuleScore
默认权重     0.30            0.35              0.20               0.15
```

两处关键处理：

- **权重重归一化** —— 某模态无有效信号时（可见光未检出缺陷、无规则命中），
  该模态被整体剔除，剩余权重按比例重新分配到 1.0，避免缺失模态把总分「压低」。
- **一致性加成** —— 三个及以上模态同时指向异常（分数 > 60）时额外加分，
  反映多源印证带来的置信度提升。

风险分级边界（闭区间下界）：`0–30 正常` / `30–60 关注` / `60–80 异常` / `80–100 严重异常`。

### 2.4 规则引擎与知识分析层

规则引擎以 `config/rules.yaml` 驱动，18 条规则覆盖温度、温升、三相不平衡、
负载、负荷趋势等判据，命中后输出带严重度权重的 `RuleScore`。

RAG 层加载 PDF / Word / 标准文档（PyMuPDF、python-docx），按段落聚合切分并保留重叠，
默认使用离线可用的字符 n-gram TF-IDF 嵌入，索引为空时安全降级。

大模型层抽象为 `LLMProvider`，提供 `mock` / `dashscope` / `openai` 三种实现。
`mock` 为模板化生成，完全离线、确定性输出，用于打通全链路与回归测试；
接入真实模型只需配置环境变量密钥（`DASHSCOPE_API_KEY` / `OPENAI_API_KEY`），
密钥通过 `api_key_env` 引用，**不落配置文件**。

最终由报告生成器输出结构化 Markdown 巡检报告，包含设备信息、各模态检测明细、
风险等级、融合计算过程、依据标准与处置建议，并附免责声明。

## 三、最终效果

### 3.1 端到端运行结果

`scripts/run_demo.py` 对 5 个合成场景跑通全链路（无训练权重，两个视觉分支运行在降级模式）：

| 场景 | 真值 | 系统判级 | RiskScore | 关键中间量 |
| --- | --- | :---: | ---: | --- |
| `normal` | 无缺陷 | 正常 ✅ | 3.18 | Tmax 40.78℃，ΔT 6.13K |
| `oil_leak` | 渗漏油 + 油污 | 正常 ❌ | 3.18 | 可见光未检出；ΔT 2.57K |
| `foreign_object` | 悬挂异物 | 正常 ❌ | 3.18 | 可见光未检出；Tmax 39.18℃ |
| `overheat` | 接线端子过热 | **异常** ✅ | **79.47** | Tmax 97.26℃，ΔT **44.54K**，δ 61.64%，命中 7 条规则 |
| `critical` | 破损 + 锈蚀 + 严重过热 | **异常** ✅ | **67.86** | Tmax 118.64℃，ΔT 65.99K，命中 5 条规则 |

`overheat` 场景的融合明细，完整体现了「红外为主、时序印证、规则加权」的决策路径：

```
红外 100.0×0.50 = 50.0   ← 热级别 critical，权重因可见光无信号而抬升
时序  35.6×0.29 = 10.2   ← 检出 load_rise，负荷上升比 0.45
规则  90.0×0.21 = 19.3   ← 命中相对温差严重、绝对温度超限、三相不平衡等
      ─────────────────
RiskScore        79.47   → 异常
```

### 3.2 已验证的能力

- **红外热缺陷检测有效** —— 在无需任何训练权重的情况下（`radiometric` 路径），
  准确量化了 44.54K 与 65.99K 的严重温升，并正确触发多项规则。
- **相对温差判据的鲁棒性** —— 参考温度能自适应选择 `three_phase` 或 `warm_median` 来源。
- **权重重归一化正确** —— 可见光无信号时其权重被剔除，红外权重由 0.35 抬升至 0.50，
  报告附「权重已按比例重新分配」说明。
- **降级不崩溃** —— 无权重、无知识库、无前端时系统全程正常运行，并以 `backend` 字段
  与警告信息显式告知用户当前处于降级模式。
- **持久化与报告** —— SQLite 记录巡检历史，Markdown 报告落盘至 `data/reports/`。

### 3.3 当前局限

必须如实说明：**合成场景中两个纯可见光缺陷（`oil_leak`、`foreign_object`）被漏报**。

根因是 `models/` 为空，可见光分支运行在启发式兜底模式，5 个场景的 `VisualScore` 全为 0——
该分支目前**不具备真实的缺陷识别能力**，只能定位设备目标。因此本系统现阶段的有效性
集中在红外与时序两个分支，可见光分支需训练权重后才能发挥作用。

其余限制：

- **无 Web 前端** —— `frontend/` 未创建，需通过 `/docs` 或 curl 调试接口。
- **知识库为空** —— `knowledge/` 未创建，报告的「依据标准」章节始终为空。
- **无自动化测试** —— `tests/` 未创建。
- **合成数据不可用于精度评估** —— 仅用于流程验证与回归。
- **红外绝对温度依赖标定** —— 伪彩色与无标定灰度图只能给出相对温度分布。

### 3.4 后续工作

按优先级：接入真实数据集（CPLID / IDDD 可见光、thermal-images-equip 红外、ETT 时序）
→ 训练 YOLO 与时序模型使两分支脱离降级模式 → 构建 `knowledge/` 标准文档库
→ 实现 Web 前端 → 补充单元测试。

## 四、快速开始

```bash
cd PowerAI-Safety

# 1. 环境（需 Python 3.10+）
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt      # Linux/macOS: .venv/bin/pip

# 2. 命令行跑通全链路（推荐首先执行，无需启动服务）
python scripts/run_demo.py
python scripts/run_demo.py --scenario overheat --markdown    # 单场景 + 完整报告

# 3. 启动 HTTP 服务
python -m backend.main
# 交互式接口文档 → http://127.0.0.1:8000/docs
```

仓库内置 `data/samples/` 合成样例（5 个场景 × 可见光/红外/时序），
**零下载即可跑通全链路**。样例可重新生成：

```bash
python datasets/synthesize.py
```
